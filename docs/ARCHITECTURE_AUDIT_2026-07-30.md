# 架构、冗余变量与可维护性审计报告

日期：2026-07-30  
审计基线：`b10e073c37316633335531d704fc9f15173aa5e7`  
范围：`badge_relief_maker/`、`tests/`、CLI、桌面 UI、项目文件模型与架构文档

## 1. 结论

项目原先并不存在“大量普通局部变量定义后完全未使用”的问题；真正成规模的冗余集中在更危险的架构层面：

1. 同一组模式、默认值、别名和校验规则在项目模型、运行时参数、CLI、UI 和构建器中分别维护。
2. 连通域遍历、网格数组规范化、原子写文件、标记字段别名等基础算法存在多份近似实现。
3. 持久化项目参数到运行时参数的映射混在 `project_build.py` 中，使 GUI 预览和项目构建依赖同一个大型编排模块。
4. 桌面 UI 存在“旧窗口 + 修正版子类”两个可被导入的实现，基础窗口还保留了一套重复且坐标语义不安全的预览编辑逻辑。
5. `use_smoothed_side_walls` 等参数已经不影响产物，却仍贯穿项目模型、CLI、运行时参数和测试。
6. 早期脚手架、仅供测试的替代网格路径、从未消费的持久化字段继续占据维护面。

本轮已完成实际重构，而非只给建议。生产 Python 代码由 38 个文件、6470 行变为 45 个文件、6170 行：新增的小文件用于建立共享边界，同时删除或收敛大块重复实现，净减少 300 行。测试由 32 个文件、3175 行变为 33 个文件、3159 行；删除了只验证失效功能的测试，并新增共享契约测试。

## 2. 审计口径

“只使用一次”不是自动删除条件。一个局部变量如果表达了图像处理阶段、几何中间量或物理单位，即使只读取一次，也可能比内联表达式更易维护。本次按以下标准判断通用性：

- 是否表达跨模块共享的领域词汇、默认值或格式；
- 是否被 CLI、UI、持久化模型和运行时模型共同依赖；
- 是否包含必须保持一致的安全或正确性规则；
- 是否只是无行为参数、失效兼容层、重复别名或可重新生成的持久化数据；
- 抽取后是否能减少修改点，同时保持依赖方向清晰；
- 是否有测试能够锁定共享契约。

执行的审计包括：

- 对生产模块级函数、类和数据类字段做静态引用频率扫描；
- 搜索 `TODO`、`FIXME`、`HACK`、`legacy`、`compatibility`、`workaround` 等特殊注释；
- 搜索重复的选项集合、默认值、数值校验、连通域遍历、网格数组校验、原子替换和标记别名；
- 检查持久化字段从读取、映射到实际消费的完整链路；
- 检查 UI、CLI、项目构建与直接构建的入口是否分叉；
- 使用测试、Ruff、差异空白检查和 CLI 入口烟雾测试验证结果。

静态引用扫描是启发式证据，不代替动态调用分析。重构后的生产代码共有 265 个模块级函数/类、136 个数据类字段；在生产代码和测试的合并文本中，没有生产模块级符号总出现次数不超过 1，也没有数据类字段总出现次数不超过 2。

## 3. 主要发现与处理

| 优先级 | 原问题 | 风险 | 处理结果 |
| --- | --- | --- | --- |
| P1 | 支持值、默认值和质量别名散落在模型、CLI、UI、分析器和构建器 | 新增模式时容易漏改，默认值可能漂移 | 新建 `options.py`，由统一目录派生 choices、默认值和成员校验 |
| P1 | 项目校验与 `ReliefParameters` 映射埋在 `project_build.py`，且与单面管线重复数值校验 | 预览、文件构建和直接构建可能产生不同规则 | 新建 `validation.py` 和 `project_parameters.py`，明确“持久化模型到运行时模型”边界 |
| P1 | `main_window.py` 和 `editor_window.py` 形成两个窗口入口，基础类仍有重复编辑实现 | 导入不同模块会获得不同行为；修复可能只落到一个窗口 | `project_window.py` 只保留窗口壳和显式钩子，`editor_window.MainWindow` 是唯一具体实现，`main_window.py` 成为 3 行公共门面 |
| P1 | `use_smoothed_side_walls` 在各层传递但构建器直接丢弃 | 用户以为选项有效，维护者需要维持假行为 | 从模型、参数、CLI、构建调用、文档和专属测试中删除 |
| P1 | 四处以上实现二值图连通域遍历 | 对角连接、边界接触和遍历顺序可能不一致 | 新建 `components.py`，统一 4/8 连通、组件对象和标签网格 |
| P1 | 导出、修复、优化各自处理 `N x 3` 网格数组和有符号体积 | 对非法索引、非整数面和非有限值的处理可能分叉 | 新建 `mesh_data.py`，统一严格规范化、有效面掩码和体积计算 |
| P1 | 项目保存和网格导出分别实现临时文件、`fsync` 与替换 | 崩溃安全修复需要复制两次 | 新建 `atomic_io.py`，两类写入共用一个原子写上下文 |
| P2 | 标记形状、操作、坐标键、尺寸键和高度键在多个模块重复 | UI 写出的字段可能无法被变换器或应用器识别 | 新建 `marker_schema.py`，映射、变换和应用阶段共享词汇 |
| P2 | `project_build.py` 重复创建导出/预览目录、生成历史相对路径并包装 load/build/save | 三种构建方式的路径和保存行为容易漂移 | 新增 `ProjectBuildWorkspace` 与 `_run_project_file_build` |
| P2 | `single_side_pipeline.py` 一个入口同时承担网格构造、报告、警告和导出 | 修改报告或导出会触碰主管线 | 分解为网格、报告、警告、导出助手，主函数只负责阶段编排 |
| P2 | `OutlineData`、`layer_count` 被持久化但未被运行时消费 | 项目格式保存无效状态，未来迁移成本增加 | 从模型和格式说明删除；运行时生成的 `outline` 报告继续保留 |
| P2 | STL 单位说明、导出格式集合等常量重复 | 报告和导出元数据可能不一致 | 新建 `units.py`，格式集合归入 `options.py` |
| P2 | `app/__init__.py` 提前导入 CLI 模块，`python -m ...main` 产生运行时警告 | 模块执行顺序不清晰，导入包加载过多依赖 | 改为惰性入口，并为 `main.py` 增加标准 `__main__` 路径 |

## 4. 删除的非通用代码

以下内容没有被包装成所谓“通用工具”，而是直接删除，因为它们没有稳定的生产语义：

- `core/relief_mesh_builder.py`：未被生产管线使用的早期规则网格脚手架。
- `core/contour_side_builder.py`：仅由专属测试调用的替代侧壁预览路径，未接入任何生产构建。
- `placeholder_regions`、`align_placeholder`、`empty_heightmap`、`layered_heightmap`、`load_rgba`：没有生产调用者的占位或重复入口。
- 仅包装 front/back 内存构建、但没有调用者的两个项目构建函数。
- `use_smoothed_side_walls` 全链路及其兼容警告。
- 持久化 `OutlineData`、`ReliefSideParameters.layer_count`。
- 基础 UI 中重复且坐标语义不安全的预览刷新、点击编辑和清理实现。

项目 JSON 加载器仍会忽略未知字段，因此旧文件中残留的 `outline`、`layer_count` 或 `use_smoothed_side_walls` 不会阻止加载。需要明确的是，CLI 参数 `--smoothed-side-walls` 已被移除；它原本没有实际效果，继续接受会制造错误预期。

## 5. 重塑后的职责边界

### 5.1 共享基础层

- `options.py`：领域选项值、顺序、默认值和别名。
- `validation.py`：严格数值与整数校验。
- `marker_schema.py`：手工标记协议。
- `components.py`：像素连通域。
- `mesh_data.py`：网格数组边界。
- `atomic_io.py`：崩溃安全写入。
- `units.py`：单位约定。

这些模块没有 UI 或项目编排依赖，可同时被直接构建、项目构建、CLI 和 GUI 复用。

### 5.2 模型与适配层

- `project_model.py` 负责宽容读取的持久化数据结构。
- `relief_parameters.py` 负责不可变的运行时构建参数。
- `project_parameters.py` 负责选择项目侧、校验已保存设置、处理双面质量规则，并完成两种模型之间的映射。

这避免了让项目 JSON 数据类直接渗入图像和几何算法。

### 5.3 构建编排层

- `single_side_pipeline.py` 负责单面图像到字段、字段到闭合网格、报告和导出。
- `double_side_builder.py` 负责纯双面对齐和实体构造。
- `project_build.py` 负责项目路径、历史记录以及单面/占位/融合三种工作流。

项目文件包装器现在通过同一条 load/build/save 路径运行。

### 5.4 表现层

- CLI 从共享目录生成 choices，从 `ReliefParameters` 获取数值默认值。
- `ProjectWindow` 是可复用窗口壳。
- `editor_window.MainWindow` 实现正确的源图/最终网格坐标编辑。
- `ui.main_window.MainWindow` 是唯一公共桌面入口。

完整依赖方向与扩展规则见 `docs/ARCHITECTURE.md`。

## 8. 仍保留的维护债务

本轮没有为了追求低复杂度数字而机械拆分几何算法。扩展 Ruff 规则仍会指出以下热点：

- `manufacturability_check.py` 的报告聚合与制造门禁；
- `masked_solid_builder.py` 的索引实体构造；
- `mesh_analysis.py` 的自交与距离分析；
- `marker_transform.py` 的多坐标空间分支；
- `prepare_relief_field` 的图像处理阶段编排；
- CLI 参数声明和 Qt 表单构建等声明式长函数。

这些位置包含真实领域复杂度。下一轮应优先把“输入上下文”和“报告结果”组织成具名数据对象，并为几何不变量增加性质测试，然后再拆函数；不建议仅为了消除“参数太多/分支太多”告警而创建更多无语义包装层。

另外，当前项目文件版本仍为 2。删除的字段依靠“未知字段忽略”保持读取兼容；如果未来需要严格 schema、降级保存或对外发布稳定 SDK，应在版本 3 中正式记录迁移，而不是继续累积隐式容错。

## 9. 后续维护规则

1. 新增模式、格式或工艺类型时，先修改 `options.py`，再让模型、CLI 和 UI 引用它。
2. 新增项目字段必须同时完成：持久化字段、`project_parameters.py` 校验/映射、运行时消费、端到端测试。
3. 不允许在功能模块内重新实现连通域、网格数组校验、标记别名或原子替换。
4. 不持久化可在构建时重新生成的轮廓、报告或中间字段。
5. 新增布尔参数前必须有可观察的输出差异测试；没有行为的参数应删除，而不是保留兼容假象。
6. 单次使用但能表达阶段、单位或不变量的局部变量可以保留；只删除无行为、无调用、重复协议或纯转发别名。
7. GUI 只从 `ui.main_window` 暴露公共窗口，坐标相关编辑只由具体编辑器实现。
8. 每次涉及共享目录或项目模型的变更都运行完整测试、Ruff、CLI 入口和项目文件往返测试。
